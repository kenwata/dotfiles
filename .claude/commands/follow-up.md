前回の総点検以後に完了したタスク群と変更を横断して検査し、機械的な漏れを是正したうえで、新しいcheckpointをGit履歴へ残してください。本コマンドは節目の総点検であり、通常のT完了処理や軽量なセッション終了処理の代わりではありません。開始時に `~/.claude/templates/model-routing.md` を読み、Claude Code列の節目用モデルを使う横断検査として扱います。要点:

以下で既存表現として「セッション範囲」または「セッションの `git log` と `git diff`」と記す箇所は、Git管理下では手順2で確定したcheckpoint以後の範囲、非Gitでは手順2で確定した対象パスを指す。

1. **前提確認とモード判定**: git リポジトリか・`HANDOFF.md` があるかを確認し、次の3モードのいずれかを判定して **報告に明記する**。検査の中核(手順2・4・7)はどのモードでも必ず実行する — 縮退させるのは着地物に依存する段(手順3の②③④⑦・手順5の持ち越し先・手順6・手順7の着地物側の検査 (e)(f)(g))だけである。
   - **四層モード**: `HANDOFF.md` あり。全手順を実行。
   - **単発(git)モード**: `HANDOFF.md` 無し・git リポジトリ。手順3の②③④⑦と手順6をスキップし、手順5の判断待ちは AskUserQuestion でその場で決着させる。
   - **単発(非git)モード**: `HANDOFF.md` 無し・非 git。単発(git)モードに加え、手順2・3・4の対象特定を会話・ファイル現物ベースへ切り替える。
2. **checkpoint・範囲・正本の確定**: Git管理下では、現在HEADのfirst-parent上から、`git interpret-trailers --parse` が末尾のtrailer blockとして正確に `Follow-Up-Checkpoint: true` を返す最新コミットを探し、その直後から現在HEADと未コミット差分までを範囲とする。本文途中の同名行や引用例はcheckpointにしない。checkpointが無い場合だけ `$ARGUMENTS` のコミットを初回基準として受け付け、引数も無ければ利用者へ確認して止める。全履歴や現在HEADを黙って基準にしない。基準がHEADの祖先であることを `git merge-base --is-ancestor` で確認し、履歴改変・別系列・同一worktreeの所有不明な変更を検出したら推測せず止める。非Gitではこの実行で編集したパスと利用者指定パスだけを範囲とし、複数セッション差分を復元できない限界を報告する。範囲から、①境界付きT番号を持つコミット ②`TODO.md` の `[ ]`→`[x]` に現れるT番号、`[ ]`→`[-]`(廃止)に現れるT番号、および **範囲中に完了条件ブロックが書き換えられたT番号とその変更前の原文**(`git diff <基準>..HEAD -- TODO.md` の削除行から取る。`TODO.md` の未着手タスクは `/amend` と再計画時の `/breakdown` が書き換えてよいため、現在値だけを正にすると基準が動いたことを検出できない) ③active TODOと既存archiveの該当完了条件 ④該当Tの計画行が指す設計書 ⑤範囲中に変更された `plan.md`・設計書・`docs/decisions.md`・`docs/architecture.md` ⑥Tに紐付かないコミットと未コミット変更(要約の prefix が `amend` のコミットは設計の部分改訂であり、由来の `T<n>` と改訂対象の設計書に紐付けて扱う) ⑦**この時点で `HANDOFF.md` の「要確認」に存在する全項目**(四層モードのみ。回収対象として逐語で控える。手順 5 で本コマンドが新たに積む項目は含めず、次回の総点検へ持ち越す — 総点検自体が項目を生むため、回収対象を「開始時点に存在した項目」に固定することで、項目の寿命を最長 1 checkpoint 区間に抑える) ⑧**目標の抜粋** — ④の各設計書の「全体構想」行が `plan.md` を指すなら、その節の中のフェーズ見出しの本文と `plan.md` 冒頭の目標を、範囲中に `plan.md` が変更されたかどうかに関係なく **常に** 原文で控える(`plan.md` 全体は読まない。「全体構想: なし」なら設計書の「目的(アウトカム)」節を控える)、を収集する。照合の正は、各TではTODOまたはarchiveの完了条件と対応設計書、計画粒度では設計書と `plan.md`、どちらも無い単発変更では利用者の明示指示とする。これとは別に、**目標への照合の正は⑧の抜粋**(`plan.md` の該当フェーズ。無ければ設計書の目的、それも無ければ照合先なし)とする — 完了条件と設計書は目標へ至る中間文書であり、それだけに照らすと段ごとにたまったずれが素通りする(規則の正は BLUEPRINT §6「目標への照合」)。plan modeの一時ファイルはこの会話で明示され永続文書が無い場合だけ補助に使い、時刻順で別セッションのプランを推測しない。未分類変更は既存T・設計内か、独立タスクまたは計画変更が必要かを検査する。起点、対象T、正本、未分類変更を確定できなければ利用者へ確認する。

4. **サブエージェント検査**(セルフチェックは自分の盲点を継承するため、必ずコンテキストの外へ出す。**どのモードでも必須**。**手順 2 で基準と範囲が確定した直後に起動し、手順 3 と並走させる** — 本検査の入力は基準の原文と diff だけで着地物の更新後の状態には依存せず、手順 3 は読み取りのみで差分を変えないので並走して問題ない。起動は非同期なので完了通知を待たずに手順 3 を進める。後回しにすると約 3 分の待ちが直列に乗る。**手順 5 は本検査の結果を受け取ってから始める**(検査中に作業ツリーを変えない)): **`diff-reviewer` エージェント**(`~/.claude/agents/diff-reviewer.md`。編集・commit/push は構造的に禁止済み)を1本起動し、**渡す入力を次に固定する** — 手順2で確定した基準の原文 / git ならセッションの `git log` と `git diff`(複数リポジトリにまたがるならその全て)、非 git なら **このセッションで自分が Write/Edit したファイルのパス一覧**(パスは事実なので渡してよいが、判断・スコープ解釈は渡さない。中身はサブエージェント自身に Read させる)。**会話履歴と自分の判断・スコープ解釈の要約は渡さない**(「これは意図的にスコープ外にした」という自己弁護が混ざると照合が甘くなる)。**既知の限界**: 非 git では、触ったことを自分が忘れているファイルは検査に乗らない。git repo では `git status`(未追跡含む)がこの穴を塞ぐ。検査させるのは (a)計画が挙げた変更対象が diff(非 git ならパス一覧)に現れているか — 現れないものは「未着手」か「不要と判断した」かを区別 (b)計画の検証項目を実行したか (c)完了条件の各項目に証跡があるか (d)計画に無いのに実施したもの(逆方向の検査。**plan mode を通った回は、その成果が既存 `T<n>` の完了条件の範囲内かも判定させる** — 範囲内なら `T<n>` の実行手段であり起票不要。範囲外なら、既存設計書の部分改訂として `/amend` で取り込むか、次の計画 `#<n>+1` として `/elaborate` → `/breakdown` で起票するかをユーザー判断へ回す。振り分けの正は BLUEPRINT §6「変更の三段分類」)。(h)**基準変更の検査** — 手順2で収集した「範囲中に完了条件ブロックが書き換えられたT」について、変更前の原文と変更後を並べて渡し、その変更が `docs/decisions.md` の行と 1 対 1 で対応しているか、実装に合わせた緩和(検証項目の削除・閾値の引き下げ・`[subjective]` への変更)になっていないか、完了済み(`[x]`)のタスクの完了条件が書き換えられていないかを検査させる(該当Tが無ければこの項目は省く)。(i)**目標への照合** — 手順2の⑧の抜粋を原文のまま渡し(要約・解釈を添えない)、範囲の差分と完了したTの総体が、その目標へ向かっているかを検査させる。挙げさせるのは、目標に届かない差分、目標に届いたと観測できない点、中間文書(設計書の節・完了条件)が `plan.md` の該当フェーズから離れている箇所で、文書名と節で名指しさせる(照合先が無ければこの項目は省き、手順 9 で「照合先なし」と報告する)。着地物側の検査(次の一手に着手できるか・diff の情報の未反映・撤回済み記述の残存)は着地物を更新した後でなければ成立しないため、ここではなく手順 7 で行う。**返ってきた指摘は是正の前に実測で精査する** — fresh-context は盲点を消す代わりに会話で確立した計測手法も失っており、前例では11件中1件が取り違えだった。なお「ユーザーから修正指摘を受けた回に規約側(`CLAUDE.md` / `.claude/rules/` / auto memory)の差分がゼロで終わっていないか」は **自分で判定する** — 指摘の有無は会話にしかない情報で、上の入力定義と矛盾するため出せない。

   **要確認の回収**(**四層モードのみ**。手順 2 の⑦で控えた項目が 1 件以上ある時): 利用者が指示しなくても要確認が回収されるよう、総点検のたびに全件を問う。①まず機械チェック③で、各項目が完了条件・`docs/decisions.md`・設計文書で既に決着していないかを実測する(決着済みなら問わず、手順 6 で消す)。`/breakdown` が積んだ設計書の事実誤りの是正依頼は問わず、手順 5 の是正で直す。②残った項目を AskUserQuestion で問う(1 回 4 問まで。足りなければ回数を分ける)。問うのは手順 3 と並行でよいが、**答えの書き込みは手順 5・6 で行う**(手順 4 の検査中に作業ツリーを変えない)。回収点が `T<n> 着手前` の項目も問い、利用者が「T<n> の着手時に決める」と答えた項目だけをそのまま残す。③回収は **決めて振り分けるだけで、実行しない**: 答えは `docs/decisions.md` に 1 行(将来のタスクを縛る決定なら、タスクID列にその `T<n>` を書く — `/execute-task` が着手前に読む)、作業が要るものは「次セッションの最初の一手」へ回す(設計書や完了条件の改訂なら `/amend`)。④**問いを取りやめてよいのは、①で決着済みと実測できた時だけ**。自分の判断で決めて項目を消さない(AskUserQuestion の品質ゲートは「自分で決められるなら取りやめよ」と促すが、要確認の項目は利用者にしか決められないと既に判定された問いである)。⑤**止めない**: 利用者が不在、または答えが得られない項目が残っても checkpoint は打つ。残った項目は逐語で持ち越し、件数を報告し、「次セッションの最初の一手」を「要確認 N 件の決着。その後 <本来の次の一手>」にする(答えの出ない問い 1 件で、無関係なタスクまで止めないため)。
5. **是正**: 着地物への追記・整形・ポインタの補完は **自動で直す**(⑦の検出で `docs/architecture.md` にツリーの追記漏れがあった場合も含む)。新しいユーザー決定を要するもの・タスクの再解釈・スコープの変更は **報告に留めてユーザー判断を仰ぐ**(⑦で検出したフラット違反候補の是正としてファイルを移動する判断もここに含まれる — 移動は影響が大きいため自動では行わない)。**手順 4 の (i) の指摘は自動で直さない** — 実装・中間文書の側を戻すなら `/amend`(方針・構成・完了条件)か `/elaborate`(目的・スコープ)の実行として、`plan.md` の側が古いなら「`plan.md` を改めて `docs/decisions.md` に 1 行」として、どちらかを利用者判断へ回す(中間文書を黙って正にしない。どちらが正しいかは利用者にしか決められない)。**完了条件の書き換えとタスクの廃止(`[-]`)も本コマンドでは行わない** — 必要と判断したら、根拠を添えて `/amend` の実行をユーザー判断へ回す(総点検が基準を動かすと、基準変更の検査 (h) の検査者と被検査者が同じになる)。ただし回す前に、その論点が完了条件・`docs/decisions.md`・設計文書で **既に決着していないかを実測で確かめる** — 語の一致だけを見て母集合を取り違えると、成立しない問いをユーザーへ投げることになる。**ユーザー判断へ回すものは、報告に書くだけで終わらせない** — 四層モードでは `HANDOFF.md` の「要確認」へ、同ファイル冒頭の規約どおり回収点 `[回収: T<n> 着手前]` または `[回収: 次の /follow-up]` を先頭に付けて必ず載せる(優先度ラベルは付けない。回収点を書けないものは要確認ではなく、決定済みの事実なら `docs/decisions.md`、どの判断にも効かない気づきなら報告とコミット本文に留める)。**単発モードには持ち越し先が無いため、AskUserQuestion でその場で決着させる**(保留という選択肢を作らない — report-only にすると、HANDOFF への転記義務を追加した 2026-08-20 の失敗を単発モードで再導入することになる)。報告はセッションと共に流れ、着地物だけが次セッションへ渡る — 四層モードでは手順6の終了手順は手順5とは別の段なので、回した論点が自動では引き継がれない(2026-08-20 に実際に落ちた)。
6. **状態文書を着地させる**(**四層モードのみ**。`HANDOFF.md` が無い場合はスキップし、その旨を報告する): TODOの状態と実行系、`HANDOFF.md` の最後に完了したタスク・仕掛かり中・次の一手・要確認、該当する `docs/decisions.md` を現状へそろえる。確認済みの完了タスクにTODOのローテーション規約を適用し、逐語移動と対応ブロックの1対1を機械確認する。規定の正は `~/.claude/templates/BLUEPRINT.md` §6と各ファイル冒頭の規約コメントであり、ここへ転記しない。
7. **報告の前の完了判断レビュー**(**どのモードでも必須、1 回だけ**): **`proposal-reviewer` エージェント**(`~/.claude/agents/proposal-reviewer.md`。読み取り専用)を 1 本起動し、報告案(検出件数・是正した内容・ユーザー判断へ回す論点とその理由)と、手順 2 で確定した基準の原文、git ならセッションの `git log` と `git diff`(非 git なら Write/Edit したパス一覧)、四層モードでは手順 6 で更新した着地物(`HANDOFF.md`・`TODO.md`・`docs/decisions.md`)のパスを渡して、完了判断そのものを反証させる。**四層モードではあわせて着地物側の検査も依頼する** — (e)着地物だけで次セッションが次の一手に着手できるか (f)diff に現れる情報のうち着地物へ未反映のもの (g)`docs/decisions.md` に撤回の記録があるとき参照先文書に旧記述が残っていないか(この 3 項目は着地物の更新後でなければ成立しないため手順 4 ではなくここで行う)。手順 4 と同じく、返ってきた指摘は実測で精査してから是正し、是正後の再レビューはしない(残った論点は報告に載せる)。ここを飛ばすと、漏れチェックの結果自体が無検査で通る(2026-08-20 に実際に起きた失敗がこれである)。
8. **checkpointをコミットする**(Git管理下のみ): 総点検による是正と状態文書を1コミットにまとめ、コミットメッセージ末尾のtrailer blockへ `Follow-Up-Checkpoint: true` を必ず入れ、その後には本文を置かない。変更が無い場合も `git commit --allow-empty` でcheckpointを作り、既定の要約は `chore: follow-up checkpoint` とする。作成後に `git interpret-trailers --parse` で正確なtrailerとして読めることを確認する。プロジェクト固有のコミット書式があれば従う。コミット権限が無い場合はcheckpointを作らず総点検を未完と報告する。push・公開・デプロイは利用者の明示指示なしに行わない。
9. **報告**: モード、基準checkpoint、対象範囲とT番号、目標への照合先(`plan.md §<節番号> / <フェーズ見出し>`・設計書の目的・照合先なし のいずれか)と手順 4 の (i) の検出件数、未分類変更、検出・是正件数、検証証拠、作成したcheckpoint、要確認の回収(開始時の件数・決着した件数・持ち越した件数)、利用者判断待ちを簡潔に示す。
