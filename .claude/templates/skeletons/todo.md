## §0 セッションプロトコル

- 開始時に読む: このファイルと `HANDOFF.md` の 2 つ
- plan mode を通った時: そのプランの成果が **既存のどの `T<n>` の完了条件で検証されるか** を判定する。答えが有れば **タスク粒度**(`T<n>` の実行手段)であり `/elaborate`・`/breakdown` は実行しない。無ければ **計画粒度** であり、実装前に `/elaborate` → `/breakdown` で新しい計画行 `#<n>` を起こす。既存の設計書の一部と未着手タスクを直せば足りるなら、新しい計画行を起こさず `/amend` を使う(判定基準の正はこの行。`~/.claude/templates/BLUEPRINT.md` §6 と `CLAUDE.md` が要約する)
- 実装中に全体構想(フェーズ構成・スコープ・方針)に関わる決定が出た時: `plan.md` を更新し `docs/decisions.md` に 1 行追記する(フェーズ内の詳細は設計書へ。`plan.md` を持たないプロジェクトでは設計書と `docs/decisions.md` のみ)
- 実行中に設計の穴を見つけた時: `/execute-task` は設計書と完了条件を自分で変えず、`HANDOFF.md` の「仕掛かり中」に穴の記録(観測した事実と証拠 / 矛盾または欠落している設計書の節 / 満たせない完了条件の項目 / 停止位置と途中成果物)を書いて止まり、次の一手を `/amend T<n>` にする。設計書の「目的」「スコープ」か `plan.md` のフェーズ構成が変わる時だけ `/elaborate` へ戻る
- タスク完了ごと: ①該当タスクの状態を `[x]` に更新し、`実` 列に自分の実行系/モデルを記入(配下の全タスクが `[x]` か `[-]` になったら、冒頭コメントの「計画行の状態」の規則で計画テーブルの該当行も更新) ②git commit(要約に `T<n>` を含める。変更を生まないタスクは `git commit --allow-empty` で記録を残す)
- 終了時: 未コミット変更を確認する。最後に完了したタスク、仕掛かり中、次の一手、要確認のいずれかが変わった場合は `HANDOFF.md` を全体上書きする。続けて、状態変化の有無にかかわらず **毎回** コールドスタート確認を行う — このファイルと `HANDOFF.md` だけを読んだ新セッションが、正しい最初の一手と必要な参照先(設計書・実装箇所)を特定でき、このセッションで棄却した経路を繰り返さないか。不足があれば `HANDOFF.md` 冒頭の規約に従って全体上書きで補い(要確認の行は逐語で持ち越す。消してよいのは、決着を `docs/decisions.md` に書いた項目と、既に決着済みと実測できた項目だけ)、不足が無ければ書き換えない(過去の transcript は自動探索しない)。該当する判断を `docs/decisions.md` に追記する。開始時点で完了済み・廃止済みだったタスクを上の規約でローテーションし、終了処理の変更をコミットする。設計書全体の再照合や独立レビューは行わない
- 総点検: 最新 `Follow-Up-Checkpoint: true` 以後に完了した異なるT番号が5件に達した時、依存グループ完了時、統合前、ライブ検証前、設計変更または不整合を検出した時は、次のTへ進む前に `/follow-up` を実行する
