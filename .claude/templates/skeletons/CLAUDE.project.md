- コーディング規約: `.claude/rules/` — path-scoped で該当ファイル操作時に自動適用される。規約の追加・編集もそこで行う

## セッション運用

- 開始時: `HANDOFF.md` を読み、「次セッションの最初の一手」から着手する(`TODO.md` があればそれも読む。`plan.md`(全体構想)を開始時に読むのは次の一手が `/elaborate` の時だけ。`/breakdown`・`/amend`・`/follow-up` は手順の中で該当フェーズの抜粋だけを読む。それ以外は読まない)
- 長時間の実行で途中終了を避けたい場合: 必要に応じて `/goal <検証可能な完了条件>, or stop after 20 turns` を補助的に使う
- plan mode 承認後: そのプランの成果が **既存のどの `T<n>` の完了条件で検証されるか** を判定する(正は `TODO.md` §0)。答えが有れば **タスク粒度** — `/elaborate`・`/breakdown` を起動せず、そのまま実装に進む。無ければ **計画粒度** — 実装に着手する **前に**、同一セッション内で `/elaborate`(設計書)→ `/breakdown`(`TODO.md`)を実行する(検討の行間が生きているのは承認直後だけ)。既存の設計書の一部と未着手タスクを直せば足りるなら、新しい計画行を起こさず `/amend` を使う
- 実行中に設計の穴を見つけたら: 設計書と完了条件を自分で変えず、`HANDOFF.md` の「仕掛かり中」に穴の記録(観測した事実と証拠 / 矛盾または欠落している設計書の節 / 満たせない完了条件の項目 / 停止位置と途中成果物)を書いて止まり、次の一手を `/amend T<n>` にする。その場で直してよいのは、現物で機械的に真偽が出る参照(パス・ファイル名・識別子名)の誤りだけ(完了条件ブロックには触れない)。設計書の「目的」「スコープ」か `plan.md` のフェーズ構成が変わる時だけ `/elaborate` へ戻る(分類の正は `~/.claude/templates/BLUEPRINT.md` §6「変更の三段分類」)
- 判断に迷ったら推測で進めず、`HANDOFF.md` の「要確認」に記録して依存しない次のタスクへ進む。要確認に書くのは利用者にしか決められない問いだけで、行の先頭に回収点 `[回収: T<n> 着手前]` か `[回収: 次の /follow-up]` を付ける(書式と、問いでないものの行き先の正は `HANDOFF.md` 冒頭の規約)。回収は `/execute-task` の着手前の関門と `/follow-up` の冒頭が行うので、`/execute-task` を通さずにタスクへ着手する時は、要確認にそのタスクを回収点とする項目が無いかを先に確かめる
- タスク完了ごとに git commit(1タスク=1コミット)。メッセージ: `<prefix>: 要約`(TODO 管理下なら要約に T<n> を含める)+ 本文に「タスク: 依頼内容」「対応: どう解決したか」。変更を生まないタスク(調査・見送り判断)も `git commit --allow-empty` で同書式のコミットを残す(調査結果の要点は「対応:」に書く)。実行しないと決めたタスクは完了にせず、`/amend` で `[-]`(廃止)にする
- 過去の経緯調査: `git log --oneline -- <path>` → `git log --grep=<語>`(タスクIDは境界付き `-E --grep='T7([^0-9]|$)'` 形式で桁違いIDへの誤マッチを防ぐ)→ `git show <sha>` の順で絞り込む。`git log` の全件読み込みはしない
- 終了時: 未コミット変更を確認する。`HANDOFF.md` の最後に完了したタスク、仕掛かり中、次の一手、要確認のいずれかが変わった場合は全体上書きする。続けて毎回コールドスタート確認(`HANDOFF.md`(と `TODO.md`)だけで正しい最初の一手と必要な参照先が分かり、このセッションで棄却した経路を繰り返さないか)を行い、不足があれば `HANDOFF.md` 冒頭の規約に従って補う(過去の transcript は自動探索しない)。全体上書きの時、要確認の行は逐語で持ち越す(消してよいのは、決着を `docs/decisions.md` に書いた項目と、既に決着済みと実測できた項目だけ)。該当する判断を `docs/decisions.md` に追記し、TODOのローテーション規約を適用して終了処理の変更をコミットする。設計書全体の再照合や独立レビューは行わない
- 分解は段階ごと: `/breakdown` は設計書の最初の未分解の 1 段階だけを分解する。段階の最後のタスクが完了して設計書に `未分解` の段階が残っていれば、次の一手は `/breakdown docs/design/<slug>.md`(追記だけ。計画行は `[ ]` のまま)。支線の設計書(`plan.md` の `本流: §<節番号>` が指す節以外を「全体構想」に持つ)を分解する時は、`/breakdown` が本流の計器を示す
- 総点検: 最新 `Follow-Up-Checkpoint: true` 以後に完了した異なるT番号が5件に達した時、依存グループ完了時、統合前、ライブ検証前、設計変更または不整合を検出した時は、次のTへ進む前に `/follow-up` を実行する
- 修正指摘を受けたら: 指摘された箇所を直して作業を続ける。再発防止のルール化は、ユーザーが `/ruleize` を打った時だけ行う(自分の判断でルール化を始めない。ルール化してよいかも聞かない)。`/ruleize` が打たれた時の置き場は次のとおり
  - 特定ファイルの書式(TODO・changelog 等) → そのファイル冒頭のコメント規約に追記
  - プロジェクト全体のコード規約 → `.claude/rules/`(paths: 付き)
  - 全プロジェクト共通の規約 → `~/.claude/templates/rules/` への還元を提案
  - エージェントの振る舞い(聞き方・判断の仕方・報告の仕方) → その瞬間に発火する hook の点検リスト(`~/.claude/hooks/check-stop-question.sh`・`check-question-legibility.sh`)。成果物の中身の規則は機械検査を最優先
  - 環境固有の事実 → プロジェクト内の該当文書。auto memory は発火しないため再発防止の手段に数えない
