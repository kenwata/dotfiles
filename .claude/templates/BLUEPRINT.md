# プロジェクト初期化ブループリント

このドキュメントは `/initialize` コマンド実行時にのみ読み込まれる設計書である。
新規プロジェクト(または既存プロジェクトへの後付け)で、Claude Code 用の設定一式を
「起動時コンテキストを最小に保つ」方針で構築するための判断基準と手順を定める。

## 1. 目的と原則

最優先の目的は **セッション開始時に自動ロードされるコンテキストの最小化**。
そのために「何がいつロードされるか」を前提に配置を決める。

| 対象 | ロードタイミング |
| ---- | ---------------- |
| プロジェクト直下の `CLAUDE.md` | 毎セッション起動時(常時コスト) |
| `.claude/rules/*.md`(`paths:` frontmatter あり) | 該当パターンのファイルを操作した時のみ(起動時コストゼロ) |
| `.claude/rules/*.md`(`paths:` なし) | 毎セッション起動時(CLAUDE.md と同等) |
| サブディレクトリの `CLAUDE.md` | その配下のファイルを操作した時のみ(遅延ロード) |
| skills(`.claude/skills/`) | 起動時は description のみ。本文は呼び出し時 |
| auto memory(`MEMORY.md`) | 毎セッション先頭 200 行を自動ロード |

予算の目安:

- プロジェクト `CLAUDE.md`: **50 行以内**。ポインタ型に徹し、規約の中身を書かない
- `HANDOFF.md`(ルート直下): **40 行以内**。パス参照のみ、コードは貼らない。
  終了時に状態変化、またはコールドスタート確認での不足があれば全体上書きする(追記・ローテーションはしない。`rules/growing-docs.md` が規定)
- ルールは原則 `paths:` 付き(path-scoped)で置く。`paths:` なしで常時ロードするのは
  coding-principles / testing の 2 件までとする。**プロジェクト運用中に後から追加する
  手順書・スキーマ規約(ドメイン固有ルール)も必ず `paths:` 付きで置く**(この2件枠を侵食させない)。
  1 手順書が 25KB 超過、または複数ロール(読者)が同居している場合は、共通規律と
  ロール(読者)単位の分割を検討する(例: T2集計仕様のみを実装者向けに別ファイル分離)
- 既存プロジェクトで上記の常時コピー4件(§5)の一部が欠落していると気づいたら、
  `/initialize` 再実行(冪等)または個別 `cp` で補完する。特に `growing-docs.md` の欠落は
  TODO・changelog 系ファイルの無制限な肥大化に直結するため優先的に確認する
- `docs/architecture.md`: **80 行以内**。自動ロードなし(必要時のみ読む)。ディレクトリ配置規約の
  実体は `paths:` なしの `coding-principles.md` §13(常時ロード枠に含まれる)が持ち、本文書は
  そのプロジェクトでの適用結果(ツリーと決定表)のみを持つ

## 2. 初期化フロー(検出 → 確認 → 生成)

1. **検出(ユーザー入力なし)**: 以下を自動収集する
   - プロジェクト名: カレントディレクトリ名
   - 言語: §5 のマーカーファイルを Glob で探索
   - build / test / lint コマンド: `package.json` の scripts、`Makefile`、`justfile`、
     `pyproject.toml`([tool] セクション)、`Cargo.toml` 等から抽出
   - 一行説明: `README.md` の最初の見出し・段落から抽出
   - 目的の仮説: README・既存コード・ディレクトリ構成から「このプロジェクトで何を
     したいか」(開発 / 調査・リサーチ / 文書・図解作成 など)を推測する。
     新規の空プロジェクトでは推測不能なので、§3 の質問②で必ず確認する
   - 既存状態: `CLAUDE.md`、`.claude/` の有無と内容
   - git repo の有無: `git rev-parse --is-inside-work-tree` の成否(§6 の作業ログ層と
     §9 の初期コミット判断に使う)
2. **確認(AskUserQuestion 1 回、最大 3 問)**: §3 の表に従う
3. **生成**: §4 の構造を §9 の冪等性ポリシーに従って作成する
4. **検証**: §11 の生成後検証を実施してから完了を報告する

## 3. ユーザー入力(最小限)

| # | 項目 | デフォルト | 聞く条件 |
| - | ---- | ---------- | -------- |
| 1 | 言語構成の確認(複数選択) | 検出済み言語を事前選択 | 毎回(確認のみ) |
| 2 | 目的とロール構成 | 検出した目的の仮説に基づく提案セット(仮説が立たなければ「ロールなし」) | 毎回 |
| 3 | プロジェクトの一行説明 | README から抽出 | README が無い/空の時のみ |

質問②の出し方: 目的の仮説が立つ場合は「目的: <仮説> → 推奨ロールセット: <§7 で選定>」を
第一候補として提示する。仮説が立たない(新規空プロジェクト等)場合は選択肢として
「ロールなし(単独セッションで作業)」「開発(planner / coder / reviewer)」
「調査・リサーチ系」「文書・図解系」を提示し、Other での自由記述も受け付ける。
ユーザーの回答が自由記述だった場合、その目的から §7 の原則でロールを選定する。

これ以外は聞かない。handoff の場所は `HANDOFF.md`(ルート直下)固定。

例外: 旧方式 `.claude/handoff.md` 検出時の移行確認(§9)は、上記 1 回とは別に
追加で 1 回だけ許可する。

## 4. 生成するプロジェクト構造

````
<project>/
├── plan.md                # 初期化時は作らない。ユーザーが通常モードの壁打ちで作る全体構想(五層目。§6)
├── CLAUDE.md              # skeletons/CLAUDE.project.md から生成(30-50 行)
├── HANDOFF.md             # skeletons/handoff.md からコピー(git コミット対象)
├── TODO.md                # 初期化時は作らない。/breakdown 実行時に skeletons/todo.md から生成
├── docs/
│   ├── decisions.md       # skeletons/decisions.md からコピー(git コミット対象)
│   ├── architecture.md    # skeletons/architecture.md から生成(初期化時。既存プロジェクトは実ツリーから起こす)
│   └── design/
│       ├── <slug>.md      # 初期化時は作らない。/elaborate 実行時に skeletons/design.md から生成
│       └── index.md       # 同。設計書索引(派生ビュー。skeletons/design-index.md から生成)
├── .claude/
│   └── rules/             # §5 で選択したルールのみコピー
└── agents/                # ロールを配置する時のみ(構成は §7 で目的に応じて選定)
    └── <role>/CLAUDE.md   # 例: 開発なら planner / coder / reviewer
````

- 雛形の `{{placeholder}}` は検出値で埋める。不明なコマンドは `(未設定 — 判明したら記入)`
  と書き、**推測で捏造しない**
- `{{roles_pointer}}` はロールを配置した時のみ
  `- ロール定義: agents/<role>/CLAUDE.md — ロールセッションは cd agents/<role> で起動` に置換、
  no なら行ごと削除。`{{docs_pointer}}` は docs/ 配下に decisions.md 以外の既存ドキュメントが
  ある時のみ置換、無ければ行ごと削除(decisions.md 自体は常時生成のため条件対象外)
- `.claude/archive/` は初期化時には **作らない**(空ディレクトリは git が保持できない)。
  `rules/growing-docs.md` が初回ローテーション時に生成する

## 6. ハンドオフ五層設計とアーカイブ

| 層 | 担当 | 管理 |
| -- | ---- | ---- |
| auto memory(組み込み) | 個人的な学び・環境固有の事実・好み | Claude Code が自動管理。何も作らない |
| `plan.md`(ルート直下) | 全体構想・フェーズ構造・スコープ(最上位の why/what。状態を書かない) | git 管理。ユーザーが通常モードの壁打ちで作る。全体構想に関わる決定時に更新し `docs/decisions.md` に 1 行。`~/.claude/plans/` の plan mode プランファイル(repo 外・揮発性)とは別物 |
| `HANDOFF.md`(ルート直下) | タスク状態・仕掛かり中・次の一手・要確認 | git 管理。終了時に4項目の状態変化、または毎回のコールドスタート確認で不足があれば全体上書き(追記しない) |
| git log | タスク単位の作業ログ(何を依頼され・どう対応したか) | **1 タスク完了 = 1 コミット**。自動ロードなし、検索で必要箇所のみ引く |
| `docs/decisions.md` | 仕様解釈・設計からの逸脱・ユーザー決定(1行/件) | git 管理。タスク実行または終了処理で該当があれば追記(ローテーション対象外) |
| `.claude/archive/` | TODO・changelog 等、予算超過分の逐語退避(要約禁止) | git 管理。自動ロードなし・初回ローテーション時に生成 |

### 作業ログ層(git log)の規約

HANDOFF.md は全体上書きで過去が消え、decisions.md は判断(なぜ)しか残らない。
「何をどう対応したか」の逐語記録は git log が担う。コンテキストコストはゼロ
(自動ロードされない)で、必要時のみ検索して引く。

- **粒度**: 1 タスク完了 = 1 コミット。Claude が自動で実行する。変更を生まないタスク
  (調査・見送り判断。調査して「変更不要」と結論したタスクは成果が出ているので `[x]` であり、
  実行しないと決めたタスクの `[-]`(廃止)とは区別する)も `git commit --allow-empty` で T<n> 付きコミットを残し、
  調査結果の要点は本文「対応:」に書く(diff ゼロの作業を作業ログ層から欠落させない)
- **メッセージ書式**(prefix は feat / fix / docs / refactor / design / plan / amend / chore または
  スコープ名。design は /elaborate による設計書コミット用、plan は /breakdown による
  計画着地コミット用、amend は /amend による設計の部分改訂コミット用 — amend のコミットは
  総点検の契機になる「完了した T の件数」に数えない):

  ````
  <prefix>: <タスク要約(50字以内)>

  タスク: <何を依頼され何を達成しようとしたか(1-2行)>
  対応: <どう解決したか — 方針・主要変更点(1-3行)>
  ````

- **遡り方(全ログ読込の禁止)**: バグ調査等で過去を辿る時は、①`git log --oneline -- <path>`
  (ファイル単位)→ ②`git log --grep=<語>`(キーワード。コード片なら `-S'<code>'`)→
  ③`git show <sha>`(特定コミットの詳細)の順で絞り込み、該当コミットだけを読む。
  `git log`(引数なし)での全件読み込みはしない。TODO 管理下のタスクは要約に T<n> を
  含める(例: `fix: T7 CSV出力の文字化け解消`)ため、`git log -E --grep='T7([^0-9]|$)'` で
  タスク単位の全作業を一括で引ける(境界付き形式。裸の `--grep='T7'` は T70 等の
  桁違いIDに誤マッチする)
- **HANDOFF.md との連携**: 「最後に完了したタスク」の詳細はコミット SHA で参照する
  (作業ログの実体は git log に委譲し、HANDOFF.md は 40 行予算を守る)
- **配線**: この規約の実行実体は `skeletons/CLAUDE.project.md` のセッション運用に
  同梱されており、生成された各プロジェクトで常時有効になる(§10 と同じく本節が正であり、
  同梱側を変える時はここも直す)。後述の「更新トリガー配線の原則」のとおり、
  規約を書くだけでは形骸化する — セッション運用への同梱がその配線である

HANDOFF.md の書式規約は雛形冒頭のコメントに **テンプレート実体ごと** 同梱する(40 行以内 — 規約コメントを除いた本文の行数 /
パス+行番号参照 / 学びは書かない / 書く事実の基準 / 上書き前の振り分け / 全体上書き・追記禁止)。テンプレートは他ファイルを
参照させず自己完結させること(**循環参照の禁止**: 「テンプレートは A 参照」「A 側はテンプレートは
B 参照」のように互いを指し合うと、実体がどこにも存在しなくなる実例が確認されている。特に
TODO.md 側が完了タスクを積極的にローテーションして手放す設計のプロジェクトでは、TODO.md 内に
テンプレートの恒久的な置き場を作れないため、HANDOFF.md 自身に埋め込む一択になる)。
この規約により、次セッションは **HANDOFF.md 1 ファイルを読むだけ** で着手点が分かり、
リポジトリの再スキャンや完了済みタスクに関するファイルの再読込が発生しない。

40 行を超えそうな内容は HANDOFF.md に書かず、要約してポインタ(パス+行番号、または
`docs/decisions.md`・後述の TODO.md 等への参照)に留める。HANDOFF.md 自体はロー
テーションしない(全体上書きが前提のため `rules/growing-docs.md` のローテーション手順は
適用対象外)。TODO.md・changelog 等の伸び続けるファイルが予算を超えた場合のみ(TODO.md で逐語不変なのは完了・廃止済みの項目と archive であり、未着手タスクは後述「変更の三段分類」の経路で改訂できる)、
同ルールに従い `.claude/archive/` へ **一字一句そのまま** 移動し、移動後は元データとの
diff で無損失を機械的に検証する。archive は自動ロードされないため、肥大化しても
コンテキストコストはゼロのまま(必要時のみ明示的に読む)。

### 実行計画フェーズとの接続(/elaborate・/breakdown)

プロジェクトのライフサイクルは次の流れを標準とする(本節が正):

````
壁打ち(通常モード)→ plan.md(全体構想)→ /initialize(下地)
  → /elaborate(設計書へ。入力は plan.md の 1 フェーズ、または plan mode の承認済みプラン+会話)
  → /breakdown(TODO へ。入力は設計書だけ。1 回に 1 段階。支線なら本流の計器を通す)→ /execute-task(1タスク=1コミット)
      ├─ 段階の最後のタスクが完了し、設計書に未分解の段階が残る: /breakdown を再実行(追記だけ)
      ├─ 実行中に設計の穴を見つけたら: 穴の記録を HANDOFF.md に残して停止 → /amend(設計書の該当節と未着手タスクを一回で改訂)→ 中断した T<n> へ戻る
      ├─ コンテキストが閾値に達したら(予算停止): 作業記録と HANDOFF.md を書き、コミットせずに停止 → /clear → 同じ T<n> を作業記録から再開(変更ではないので三段分類の対象外。複数の T は hooks/lib/task-loop/ が T ごとに /clear して送る)
  → 節目で /follow-up(checkpoint間の横断総点検)
  → 次フェーズ: /elaborate へ戻る
        ├─ docs/design/<slug>.md  … 安定文書(フェーズ内の why/what。状態を書かない。plan.md のフェーズへのポインタを持つ)
        ├─ docs/design/index.md   … 派生ビュー(設計書の索引。列定義は skeletons/design-index.md が正。/elaborate が追記・/breakdown が T 列・タスクを足した /amend も T 列)
        └─ TODO.md                … 実行状態(計画 #n = plan.md のフェーズ。タスクID通し番号+完了条件)
実行中の plan mode(既存 T<n> を実行する手段の計画 = タスク粒度)は /elaborate・/breakdown の対象外
````

モデルの役割対応とエスカレーション境界は `model-routing.md` を正とする。モデル間の対応は性能等価ではなく、このワークフロー上の役割対応である。個々のTへ予定モデルを固定せず、実測に基づく対応変更は同文書へ集約する。

- **着地が必要な理由**: `plan.md` は repo 内の安定文書だが、骨子から詳細まで粒度がまちまちで
  フェーズ内の未決定事項を含む。plan mode のプランファイルは `~/.claude/plans/` にあり
  **repo 外・揮発性** で、しかも会話の検討過程を要約した骨子に過ぎない。どちらも耐久形は
  /elaborate が生成する設計書と /breakdown が生成する TODO.md である。plan.md 経路では
  **plan.md が一次情報** で、未決定事項は質問で埋める(推測で埋めない)。plan mode 経路では
  **承認直後の同一セッション** で /elaborate を行う(探索結果・代替案・意図の行間が生きているのは
  承認直後だけ)。/elaborate はプランの転記ではなく、会話コンテキストを一次情報として
  プランより詳細に起こす
- **粒度の区別(暴走防止)**: plan mode には 2 種類ある。**計画粒度**(新しいフェーズ・施策。
  既存のどの T<n> の完了条件にも収まらない)→ /elaborate → /breakdown。**タスク粒度**(既存 T<n> を
  実行する手段の計画)→ 何もしない(プランは T<n> の実行手段に過ぎず、成果は T<n> の完了条件で
  検証される)。判定基準は「このプランの成果は既存のどの T<n> の完了条件で検証されるか」
  (正は `skeletons/todo.md` §0)。区別が無かった実例: 2026-08 のプロジェクトで 25 日間に
  /breakdown が 40 回走り、タスクの実行計画がさらにタスクを産み続けた
- **タスクID(T<n>)が五層をつなぐ接続キー**: TODO.md(定義・チェック状態)⇔
  コミット要約の T<n>(git log --grep でタスク単位の全作業を抽出)⇔
  decisions.md のタスクID列(なぜ)⇔ HANDOFF.md の仕掛かり中(今)。
  通し番号・再利用禁止(規約の実体は `skeletons/todo.md` の冒頭コメントに同梱)。
  TODO.md 内のグルーピング・ソート用インデックス `#<n>`/`#<n>-<m>` は表示専用であり、
  五層の接続には使わない(接続キーは常に T<n>)。プロジェクトが plan.md を持つ場合、
  計画 `#<n>` は plan.md のフェーズに対応する(1 フェーズ = 1 回の /elaborate = 1 設計書 = 1 計画行)
- **五文書の境界**: plan.md = 全体構想(フェーズ構成・スコープ・方針。最上位の why/what)、
  設計書 = フェーズ内の why/what(安定・状態を書かない)、TODO.md = 実行状態、
  HANDOFF.md = 今、**docs/architecture.md = 今の形**(ディレクトリ構成。こちらも安定文書で
  状態を書かない)。**境界を跨ぐ転記が形骸化の始まり**(転記は必ず drift する。
  ポインタで参照する)。**`docs/design/index.md`(設計書索引)は五文書に含めない** —
  各設計書の実体(`# 設計: <表題>` 見出しと「全体構想」行)と git の追加履歴から起こす
  **派生ビュー** であり、正を持たない。内容を写すのではなく実体から導出するため転記禁止に
  反しないが、正でないので索引を根拠に設計判断をしない(必ず設計書本体を開く)。導入の理由は、
  設計書が増えるとファイル名からは作成順が追えず、名前が似た設計書(`deck-` で始まる 5 件が
  同一プロジェクトに実在した)の内容を判別できなくなること。書式・列定義の正は
  `skeletons/design-index.md` 冒頭コメント、更新の配線は `/elaborate`(新規行)・
  `/breakdown`(`T` 列)・`/follow-up` 機械チェック⑩(漏れと食い違いの検出)
- **plan.md の更新契機**: 全体構想に関わる決定(フェーズ構成・スコープ・方針の変更)が
  /elaborate の対話や実装中に出たら、plan.md を更新し `docs/decisions.md` に 1 行追記する。
  フェーズ内の詳細は設計書に書く(plan.md に書き戻さない)。plan.md を持たないプロジェクト
  (plan mode 起点のみ)では、設計書の「全体構想」行は「なし」とする
- TODO.md・docs/design/ は初期化時には作らない。設計書は /elaborate が
  `skeletons/design.md` から、索引 `docs/design/index.md` も /elaborate が
  `skeletons/design-index.md` から、TODO.md は /breakdown が `skeletons/todo.md` から生成する
- **`docs/architecture.md` の配線**: `/initialize` が生成(新規プロジェクトは検出言語の標準
  レイアウトから初期形を、既存プロジェクトは実ツリーから起こす)。`/elaborate` は計画が新規
  ディレクトリを要する時、実装着手前にツリーと決定表を更新する。`/follow-up` は節目の総点検時に
  実ツリーとの乖離を機械検査する(§11 と同じ検証を差分検査として流用)。加えて機構側の安全網として
  `hooks/check-new-directory.sh`(PreToolUse)が新規ディレクトリ作成時に `docs/architecture.md` の
  確認を促す(Write 経由の作成のみ検知。`mkdir` 等はプロンプト側の配線が一次的な強制手段)。
  規約が書くだけで形骸化した過去の失敗(直下の「更新トリガー配線の原則」)を繰り返さないための配線

**更新トリガー配線の原則**: 状態ファイルは「いつ読むか・いつ書くか」を必ずセッション
プロトコル(CLAUDE.md の「セッション運用」節、または TODO.md を持つプロジェクトでは
TODO.md 冒頭の §0 セッションプロトコル)に明文で配線する。配線のない状態ファイルは
更新されなくなり形骸化する — 実例: 旧方式の `.claude/handoff.md` は「セッション終了時に
更新」という規約こそあったが、それを実行させる作業儀式が存在しなかったため更新が
自然に止まり、後に別方式へ置き換える手戻りが発生した。ルールを書くだけでは不十分で、
**そのルールを実行させる手順自体を作業フローに埋め込む** ことが必須。

**プロジェクトが実行計画(TODO.md 等)を持つ場合**: HANDOFF.md(今の状態)と TODO.md
(実行計画・チェックリスト)は **分離を保つ**。過去、読みにくさの解消策として「一方の
ファイルへ統合する」判断がなされた実例があるが、これは誤りだった — 統合後も更新トリガー
配線漏れという根本原因は解消されず、後日「本来は分離構成が望ましかった」として再分割
する手戻りが発生している。**ファイル数を減らすことは解決策ではない。** 正しい対処は、
TODO.md 冒頭に §0 セッションプロトコルを置き、「開始時に読む2ファイル(TODO.md・
HANDOFF.md)」「T完了時は `/execute-task` が完了条件照合とタスク単位の着地を担う」
「セッション終了時は中断状態だけを軽量に引き継ぐ」「節目では `/follow-up` が前回checkpoint
以後を横断して総点検する」を明文化することである。更新手順の実体は本節が持つ:
① TODO.md の該当タスクと実行系を更新してT単位でコミット ② 状態が変わった場合、または
毎回行うコールドスタート確認で不足が見つかった場合だけ HANDOFF.md を全体上書き(確認の基準は
`skeletons/todo.md` §0、書く事実の基準と上書き前の振り分けは `skeletons/handoff.md` 冒頭コメントが正) ③ 該当すれば docs/decisions.md へ追記 ④ TODO.md から、
セッション開始時の HEAD 時点で既に `[x]` または `[-]` だったタスクを `.claude/archive/TODO.md` へ移す
(手順の実体は `skeletons/todo.md` の規約コメントが正。当該セッションで `[x]`・`[-]` にしたタスクは
移さない)。軽量終了処理では設計全体の照合や独立レビューを行わない。`/follow-up` は、最新の
`Follow-Up-Checkpoint: true` 以後に完了した異なるT番号が5件に達した時、依存グループ完了時、
統合前、ライブ検証前、設計変更または不整合を検出した時に実行し、完了時に同トレーラーを持つ
checkpointコミットを残す。
TODO.md の実体(§0 の文言・タスクID規約を含む)は `skeletons/todo.md` から生成する
(通常は /breakdown が行う)。規約の実体は skeleton 冒頭のコメントに同梱されて
自己完結しており、本節は設計理由のみを持つ(循環参照の回避)。

**将来の拡張継ぎ手**: TODO.md の表(計画 / #<n>-<m> / T<n> / タスク /
実行系-モデル / 状態)の列構成はそのまま関係スキーマになる。クエリ性・不変条件の
機械保証が必要になった時点で `.claude/tasks.yaml` を正とし、`TODO.md` を `yq` 生成の
ビューへ移す。SQLite は `git diff` でタスク定義の変更履歴が追えなくなるため、
複数プロジェクト横断のダッシュボードが必要になるまで見送る。

### 変更の三段分類(参照の訂正 / 部分改訂 / 再計画)

実行中や総点検で「設計書または TODO を変える必要」が出た時は、変更の大きさで経路を分ける(本節が正)。
判定は「設計書のどの節が変わるか」と「完了条件に触れるか」で行う。目的は、**修正の大きさに、読む量・
使うモデル・増えるタスク数を比例させる** ことである。

| 段 | 判定 | 経路 | モデル(正は `model-routing.md`) |
| -- | ---- | ---- | ------------------------------ |
| 参照の訂正 | リポジトリの現物で機械的に真偽が出る参照(パス・ファイル名・識別子名)の誤りだけ。完了条件ブロックには触れない | `/execute-task` がその場で直し、`docs/decisions.md` に 1 行、同じ T のコミットに含めて続行 | 実行中のモデル |
| 部分改訂 | 分解済み(`TODO.md` に計画行がある)の設計書で、「方針・構成」節、または完了条件(測り方を含む)が変わる。「目的」「スコープ / 非スコープ」と `plan.md` のフェーズ構成は不変。利用者が指示する単発のタスク追加もここ | `/amend`(設計書の該当節・未着手タスクの書き換え・最小限の追加・廃止を一回で着地。新しい計画行は作らない) | 設計の部分改訂の役割 |
| 再計画 | 「目的」「スコープ / 非スコープ」または `plan.md` のフェーズ構成が変わる | `/elaborate`(既存設計書の更新)→ `/breakdown`(同じ計画行の未着手タスクの書き換え・廃止・追記) | 計画工程 |

この表は「既にあるものを変える」時の振り分けである。設計書に並べた次の段階を `/breakdown` が同じ計画行へ
追記するのは変更ではなく当初の計画の続きであり、表の対象外(後述「段階的分解」。権限は追記だけ)。

- **区別が無かった実例**: 変更の権限が「一切変えない(`/execute-task`)」と「計画粒度でやり直す」の
  2 段しか無かった 2026-09 の 2 プロジェクトで、(a)穴一つのために最上位モデルで設計書全体を
  読み直す (b)1 件だけのタスク追加に `/breakdown` を流用する (c)既存タスクを書き換えられないので
  整合を取るための別タスクを積む (d)無効になったタスク数十件が `TODO.md` に有効な顔で残り、
  無効の事実は全体上書きされる `HANDOFF.md` にしか無い、が同時に起きた
- **未着手タスクは書き換える。補償タスクを積まない**: 不変なのは `T<n>`・`#<n>-<m>`・完了済みと
  廃止済みの項目・archive だけ。経緯は git 履歴と `docs/decisions.md` が持つ
- **基準を動かす者と検査する者を分ける**: `/execute-task` は完了条件に触れない。完了条件を
  変えられるのは利用者の承認を経る `/amend` と再計画時の `/breakdown` だけで、`/follow-up` が
  変更前の原文と `docs/decisions.md` を突き合わせ、実装に合わせた緩和でないかを検査する
  (`/follow-up` 自身は完了条件を変えない)
- **穴の記録**: `/execute-task` は設計の穴で止まる時、`HANDOFF.md` の「仕掛かり中」に 4 項目
  (観測した事実と証拠 / 矛盾または欠落している設計書の節 / 満たせない完了条件の項目 /
  停止位置と途中成果物)を書く。安いモデルが観測で記録を作り、部分改訂のモデルは記録と
  該当節だけを読む
- **廃止(`[-]`)**: 実行しないと決めたタスクは、消さず・完了にもせず `[-]` にして理由と置き換え先を
  行に書く(規約の実体は `skeletons/todo.md` 冒頭コメント)。archive へ移っても廃止と分かる
- **追加の歯止め**: `/amend` の 1 回の実行で追加できるタスクは 3 件まで。超えるなら利用者に
  「続行 / スコープ削減 / 廃止」を選ばせる。後から足したタスクは完了条件ブロックの `[由来: …]`
  タグで数えられる

### 上下流の分業と自走できるタスク記述

設計と計画は上位モデル、実装は通常実装の役割のモデルが担う(役割と目的の正は `model-routing.md`)。
目的は品質ではなく、上位モデルの利用枠を設計と計画に充てることである。実行中に計画工程へ戻ると
その枠を消費するので、通常実装のモデルが上位モデルの判断なしに走り切れる設計書とタスクを書く。

- **実例**: 2026-09 のプロジェクトでは、利用者が `/elaborate` と `/breakdown` のたびに「通常実装の
  モデルで自走できるように」と手で指定しており、完了 77 件中 74 件を通常実装のモデルが単独で完了させた。
  指定が作っていたのはタスクの細かさではなく、設計書の「裁量と停止条件」(固定するもの / 裁量に任せる
  もの / 固定を満たせない時は変更せずに止まる)「/breakdown への指針」「落とし穴」の節(雛形では
  「実行者の裁量と停止条件」「段階と分解の指針」「落とし穴」)と、番号付きの項(タスクが「第 n 項」で名指しする)、`TODO.md` の
  計画ごとの「共通の前提」だった。名前や分け方を明示的に裁量へ渡したタスクも完了しており、効いて
  いたのは判断を無くすことではなく、固定と裁量の境界を引くことだった
- **判定を要する規則は設計書で確定する**: 段階の境界、採否、閾値を設計書で決め、タスクには規則に
  当てはめる作業だけを残す。裁量で決めた点は実行者が `docs/decisions.md` に残し、後続のタスクが読む
- **共通の前提は計画につき 1 回**: 設計書のどの項を読むかと停止の規則を、計画セクションのタスク表と完了条件
  ブロックの間に書き、
  各タスクは項を名指しする。`TODO.md` は全セッションが毎回読むので、設計書に書いてあることを完了条件へ
  転記しない(同じプロジェクトで完了条件 1 本が中央値 約 1,900 文字、最大 約 6,500 文字まで膨らんでいた)
- **足りないのが記述なら割らない**: 分割の理由は 大きさ / 外部状態の境界 / 検証者または実行者が別 /
  依存 のどれかで言えること。細かく割るほど件数が積み上がり、着手前に陳腐化する
- **個々の T に予定モデルは付けない**: 全タスクに共通の実行者の基準を置くだけで、`TODO.md` にモデルの
  事前選択は持たせない。詰まった時は `/execute-task` の既存の停止条件とエスカレーション提案に任せる
- **1 タスク = 1 セッションは機構で回す**: 複数の T を続ける時は、利用者が手で打っていた `/clear` → `/execute-task` を
  `hooks/lib/task-loop/` のループが代行する(1 つのセッションに T を積まない)。次の T へ進む判定は成果物だけ
  (`TODO.md` の `[x]`・T を含むコミット・作業ツリーが clean)で行い、エージェントの報告文は判定に使わない。
  実行中に文脈が閾値に達したら `/execute-task` は作業記録を書いて止まり、同じ T を新しいセッションで再開する
  (予算停止。正は `commands/execute-task.md` 手順4)。計画工程のうち `/amend`(穴の記録で止まった T)と
  `/breakdown`(次の一手が次の段階の分解)も同じループが新しいセッションで送り、着地を成果物(コミットと
  `HANDOFF.md` の次の一手)で確かめて T の実行へ戻る。`/elaborate` は対話で詰める工程なのでループに入れず、
  次の一手が `/elaborate` になったらループは止まる。問い(承認・関門・要確認の回収)が出たらループは止まらず
  利用者の答えを待つ。計画工程のコマンドは、着地した時と `/elaborate` へ回す時の結論を `HANDOFF.md` の次の一手と
  コミットに残す(それ以外の停止は何も残さず、ループは「着地しなかった」として止まって人へ渡す)

### 本流の計器(支線の積み増しを見える形で通過させる)

支線(道具立て・基盤整備など、本流を止めて行う計画)は、毎回 `plan.md` に正式に追記され利用者も
承認するので、「目的・スコープが変わるなら再計画」の関門を素通りする。足りないのは、積み増す瞬間に
本流の停止が数字で見えないことである(本節が正。計算の実体は `hooks/lib/mainline-gauge/`)。

- **区別が無かった実例**: 2026-09 のプロジェクトで、本流のフェーズを 30 件へ分解して 5 件を完了した後、
  2 日間に支線の `/breakdown` が 5 回着地して 48 件が積まれ(12 → 13 → 16 → 1 → 6)、その間の
  本流の完了は 0 件だった。積み増しは 5 回とも `/breakdown` を通り、`/amend` 経由は 0 件だった
- **本流の宣言**: `plan.md` に固定書式の 1 行 `本流: §<節番号>`。設計書の「全体構想」行がその節を
  指せば本流、それ以外なら支線。設計書には書かない(全体構想の事実の転記になる)。宣言の無い
  プロジェクトと `plan.md` の無いプロジェクトでは、計器は何も出さない
- **出口は 1 か所**: `/breakdown` が支線の設計書を分解する前。`/elaborate` の時点ではタスクの件数が
  まだ無く、`/follow-up` は要確認の全件を既に問うので、計器を二重に出さない
- **数え方**: 完了と採番の時刻は、コミット要約ではなく `TODO.md` と archive のタスク行の差分から取る
  (要約の prefix は不揃いで、checkpoint のコミットも T を含む)。archive への逐語移動は数え直さない
- **発火の判定**: 支線のタスクが最後に採番された時点(直前の支線の分解。`/amend` による支線への追加も含む。
  コミット要約の prefix には頼らず、タスク行が最初に現れたコミットで取る)より後に、本流の完了が 1 件も
  無い時(`consecutive_side_breakdown: yes`)
  だけ、「このまま分解する / 支線のスコープを削る / 本流へ戻る」を利用者に選ばせ、`docs/decisions.md` に
  1 行残す。上の実例に当てると、1 回目の支線は表示だけ、2 回目以降の 4 回が問いになる。件数の閾値と、
  再発火を抑える状態の記録を持たない(段階的分解を入れると本流の未完了件数は常に小さくなり、件数の比は
  分母として意味を失う)
- **止めない。ただし AI が代わりに答えない**: 支線は利用者が意図して選ぶものでもある。計器の役割は、選んだことを
  見える形にすること。導入の翌日に、計器が `yes` を出したのに AI が過去の決定から「続行だろう」と推し量り、
  利用者に問わずに分解した実例がある。問わずに進めてよいのは、利用者が同じ支線について「閉じるまで続行する」と
  答えた行が `docs/decisions.md` にある時だけ(形骸化を避けるための選択肢であり、AI の推測の置き場ではない)

### 段階的分解(後半のタスクを、前半の事実の前に確定させない)

- **区別が無かった実例**: 同じプロジェクトで、一括分解した 30 件のうち残りの 25 件は、支線の移行後に
  コマンドの読み替えが必要になった。支線の 16 件の波のうち 10 件は、翌日の設計改定で「今の完了条件の
  まま着手しない」と凍結された。段階的な分解は、行数予算を理由に規約の外で既に自然発生していた
- **1 回の分解は 1 段階**: `/elaborate` が設計書の「方針・構成」に段階(完了すると検証可能な中間状態に
  達する、実装の順序のまとまり)を並べ、`/breakdown` は最初の未分解の 1 段階だけを分解する。残りは
  設計書にだけ置き、`TODO.md` に見出しだけの行を作らない。件数の上限は置かない(段階の切り方と
  行数予算が歯止め)
- **`未分解` の行と計画行**: 設計書の「タスク分解」節に、行頭の固定書式 `段階 <n>: 未分解` の行が残る間、`TODO.md` の計画行は
  配下が全て完了しても `[ ]` のまま(規約の実体は `skeletons/todo.md` 冒頭コメント)。完了扱いにすると
  計画行とセクションが archive へ移り、次の段階の追記先が消える
- **次の段階の分解は追記だけ**: 既存の未着手タスクの書き換え・廃止は `/amend` か再計画時の `/breakdown`
  に限る(「基準を動かす者と検査する者を分ける」を緩めない)。後続の段階が前の実装と合わなくなって
  いたら、分解せず `/amend` へ戻す
- **前提の検証の前倒し**: 設計書の「前提と確かめ方」のうち、読むだけで確かめられる前提は `/elaborate` が
  コミット前に確かめる。実装しないと確かめられない前提は、最初のタスクの完了条件に含める(検証の
  ためだけのタスクや、確かめたかどうかの状態の記述は増やさない)

### 要確認の回収(溜まり続けることを防ぐ配線)

`HANDOFF.md` の「要確認」は書くのにコストがかからず、全体上書きでも生き残るため、回収の担当工程が
無いと溜まる一方になる(書式と入口の選別の正は `skeletons/handoff.md` 冒頭コメント)。

- **区別が無かった実例**: 2026-09 の 2 プロジェクトで、8 日間に 75 項目(うち 29 項目が「急がない」付き)・
  最長 30 コミット生存・`HANDOFF.md` が一時 53 行、もう一方で 82 項目・最長 28 コミット生存。中身は
  利用者の判断待ち / 特定タスクの着手前の関門 / 決定済みの制約・承認 / 欠陥の指摘 / どの時点にも
  効かない気づき、の混在だった。回収は利用者が指示した時にしか起きなかった
- **全項目に回収点**: `[回収: T<n> 着手前]` か `[回収: 次の /follow-up]`。回収点を書けないものは要確認では
  ない。優先度ラベル(「急がない」)は放置の許可証になるので使わない
- **回収する工程は二つ**: `/execute-task T<n>` の着手前の関門(対象 T を回収点に持つ項目を機械的に
  抜き出して問う)と、`/follow-up` の冒頭(開始時点に存在した全項目を問う)。総点検自体が項目を生むので、
  回収対象を「開始時点に存在した項目」に固定し、今回生んだ項目は次回へ持ち越す。寿命は最長 1 checkpoint 区間
- **回収は決めて振り分けるだけ**: 答えは `docs/decisions.md` に 1 行。作業が要るものは次の一手か `/amend` へ
- **決定済みの制約は要確認に置かない**: `docs/decisions.md` のタスクID列に縛られるタスクを書き、
  `/execute-task` が着手前にその列を読む(TODO の書き換え権限を広げずに、制約を実行者へ届ける)
- **止めない**: 答えが得られなくても checkpoint は打ち、止めるのは関門に当たったタスクだけ。
  完了 T が 5 件で次の T に着手できない規則と重なると、答えの出ない問い 1 件で全体が止まるため
- **関門を通らない着手への安全網**: SessionStart hook `hooks/check-handoff-stale.sh` が、要確認の件数と
  回収点を持たない行の件数を起動時に知らせる

### 規約改訂を既存プロジェクトへ届ける手順

既存プロジェクトの `TODO.md`・`HANDOFF.md` 等は **自身の冒頭コメントを正とする**(各コマンドは
既存ファイルを新形式へ勝手に変換しない)。したがって `skeletons/` の規約を改訂しても、既存
プロジェクトには届かない。届ける時は、プロジェクトごとに次を 1 コミットで行う:

1. `diff` で、プロジェクトのファイル冒頭コメント・§0 と `skeletons/` の現行版との差を取り、
   プロジェクト固有の記述(パスの読み替え、固有の列、固有の例外)を特定して保持する
2. 改訂された規約の段落だけを冒頭コメント・§0 へ移す(表の本体・タスク行・完了条件ブロックには触れない)
3. 同梱先を同じコミットで同期する: プロジェクトの `CLAUDE.md`(または `AGENTS.md`)のセッション運用、
   `.claude/rules/`(および `.codex/rules/`)の該当ルール、archive の冒頭コメント
4. `/follow-up` 機械チェック⑧相当(追記位置マーカーの本数、タスク行と完了条件ブロックの 1 対 1。`共通の前提(` で始まる段落は対象外)を
   実行し、移行で構造を壊していないことを確認する

コマンド側は、冒頭コメントが新しい規約(未着手タスクの書き換え、`[-]`)を定義していない
ファイルには新しい操作を着地させず、本手順による移行が先に必要だと報告して止まる。

## 7. ロール配置パターン(agmsg)

**選定原則**: `~/.claude/templates/roles/` は固定セットではなく **カタログ** である。
プロジェクトの目的に合うロールだけを選び、邪魔になるロールは置かない。

- 開発(純粋なコーディング): `planner.md` / `coder.md` / `reviewer.md` が定番
- それ以外の目的: カタログ内の各ロールの frontmatter・冒頭を読んで適合を判断する
  (例: 文書・図解系なら orchestrator / content-architect / renderer 等が候補)
- **カタログに合うものが無い場合**: 目的からロール CLAUDE.md を新規に起草する。
  既存ロール(特に planner / coder / reviewer)の構造 — 運用原則・ハンドオフ契約・
  チェックリスト — を骨格として流用する。汎用性がありそうなら、ユーザーに確認のうえ
  `~/.claude/templates/roles/` へも保存して再利用可能にする(還元)
- 提案するセットは 2〜4 ロール程度に抑える。「作る役」と「検証する役」の分離を基本形とする

**配置ルール**:

- ロール指示は `agents/<role>/CLAUDE.md` に置く。`~/.claude/templates/roles/<role>.md` の
  **コピー** とする(`@import` は起動時即時展開でコンテキスト削減にならず、
  `~/` 参照は他マシンで壊れるため不採用)
- サブディレクトリ CLAUDE.md の遅延ロードにより、ロール指示はそのディレクトリ配下を
  操作するセッションにしかロードされない
- ロールセッションの起動: `cd agents/planner && claude`(プロジェクトルートの
  CLAUDE.md も祖先として自動ロードされる)
- `agents/<role>/` は CLAUDE.md の置き場であり、成果物は通常のリポジトリ構造に置く

## 8. /goal 運用指針

- `/goal` は、長時間の実行で途中終了を避けたい場合などに補助的に使う
- 完了条件は Claude の出力で検証可能な形で書く(例: 「test/auth の全テストがパスし
  lint が警告ゼロ」)。外部チェックに依存する条件は書かない
- 状態確認は `/goal`(引数なし)、解除は `/goal clear`

本節が正であり、要約は `skeletons/CLAUDE.project.md` のセッション運用に同梱されて
いる。同梱側を変える時はここも直す。

## 9. 冪等性ポリシー(既存プロジェクトへの適用)

- **上書き禁止**: コピーはすべて `cp -n`、生成は存在チェックを先に行う
- macOS(BSD cp)の `cp -n` は既存ファイルをスキップした時に **exit 1** を返すが、
  これは失敗ではなくスキップである。エラー扱いせず「既存のためスキップ」と報告する
- **既存コピーの更新は冪等化の対象外**: ロールファイル(`agents/<role>/CLAUDE.md`)・
  rules の既存コピーは `cp -n` がスキップするため、テンプレート改訂後に再 `/initialize`
  しても更新されない。テンプレート改訂を既存プロジェクトへ反映したい場合は、
  手動で diff を取り個別に更新する
- **git init と初期コミット**: 既に git repo なら `git init` しない。git repo でなければ
  `git init` を実行し、生成ファイルのみを個別パス指定で `git add` して初期コミットする
  (自動でよい — 新規 init なら他の変更が混在しえないため)。既存 repo では未コミットの
  変更が混在しうるため、生成ファイルのコミットは実行前に軽く確認を取り、拒否されたら
  スキップとして報告する。初期コミットのメッセージも §6 の書式に従う
- 既存の `CLAUDE.md` がある場合: 上書きせず内容を分析し、不足している節
  (ポインタ / セッション運用)のみを diff 提示のうえ承認を得て追記する
- スキップした項目は理由付きで全件報告する
- 再実行しても変更ゼロ(全スキップ報告のみ)であること
- **旧方式 `.claude/handoff.md` を検出した場合**: 無断で削除・移行しない。内容を
  `HANDOFF.md`(ルート直下)の新形式(4節)へ移す提案を AskUserQuestion で行い、
  承認を得てから ①内容を新形式に整形して `HANDOFF.md` へ Write ②旧 `.claude/handoff.md`
  を削除 ③`.claude/rules/growing-docs.md` の `paths:`/budget が旧パスのままなら
  §11 の生成後検証に従って新パスへ更新、の順で実施する

## 10. 再発ミスのルール化プロトコル

トリガー: ユーザーが `/ruleize` を打った時だけ(`~/.claude/commands/ruleize.md`)。修正指摘・
ヌケモレの指摘を受けただけでは、指摘された箇所を直して作業を続ける。エージェントの判断で
ルール化を始めず、ルール化してよいかも聞かない(何を恒久の制約にするかはユーザーが決める)。
`/ruleize` が打たれた時は、スコープに応じた次の行き先へ規約化する。

| スコープ | 行き先 |
| -------- | ------ |
| 特定ファイルの書式(TODO・changelog 等) | そのファイル冒頭のコメント規約に追記(無ければ作る) |
| プロジェクト全体のコード規約 | `.claude/rules/*.md`(paths: 付き)に追加 |
| 全プロジェクト共通の規約 | ユーザー確認のうえ `~/.claude/templates/rules/` へ還元(§7 のロール還元と同じ流れ) |
| エージェントの振る舞い(聞き方・判断・報告) | その瞬間に発火する hook の点検リスト(`~/.claude/hooks/check-stop-question.sh` 等)。auto memory は発火しないため再発防止に使わない |
| 環境固有の事実 | プロジェクト内の該当文書 |

この振り分けの要約は `skeletons/CLAUDE.project.md` のセッション運用に同梱されており、
生成された各プロジェクトで常時有効になる。本節が正であり、要約を変える時はここも直す。

配置の一般原則(コンテキストコストと drift リスクによるルーティング)は
`rules/growing-docs.md` の「Placement of durable rules」が正であり、本節は
再発ミス検出時のルーティングに限定する。

## 11. 生成後検証(初期化完了を報告する前に必ず実施)

以下5点を機械的に確認してから §2 の報告(作成/スキップ一覧)を行う。手作業の目視確認
だけに頼らない — frontmatter のような機械的トリガーの陳腐化は、動作させるまで気づけない。

例外: 遅延生成ファイル(`.claude/archive/` — 初回ローテーション時に生成、
`docs/design/`(`<slug>.md` と `index.md`)— /elaborate 実行時に生成、`TODO.md` — /breakdown 実行時に生成、`CHANGELOG` 等)の不在は
エラー扱いしない。ポインタ実在確認(1)および `paths:` 一致確認(2)の対象から除外する。

1. **ポインタの実在確認**: `CLAUDE.md`(および `HANDOFF.md` ヘッダコメント)が言及する
   全パス(`.claude/rules/`、`HANDOFF.md`、`docs/decisions.md`、`agents/<role>/CLAUDE.md`
   等)が実際に生成されているか、`ls`/`test -f` で確認する
2. **`paths:` frontmatter の一致確認**: `.claude/rules/*.md` の frontmatter にある
   `paths:` リストを `rg -n 'paths:' -A5` 等で洗い出し、そこに書かれたパスパターンが
   生成した実ファイル(`HANDOFF.md` 等)と一致するか確認する。文字列としての言及
   (プローズ)だけでなく frontmatter も対象にする — 一致していないとルールが
   その対象ファイル操作時に自動適用されず、静かに機能停止する
3. **循環参照がないことの確認**: テンプレート実体や規約文言を「他ファイル参照」に
   している箇所があれば、参照先を実際に開いて実体が存在することを確認する。
   両者が互いを指し合っている(循環している)場合は、どちらか一方に実体を埋め込んで
   自己完結させてから報告する
4. **git repo であることの確認**: `git rev-parse --is-inside-work-tree` が成功すること。
   新規に `git init` した場合は、初期コミットが存在すること(`git log --oneline -1`)も
   確認する(§6 の作業ログ層は git repo が前提のため)
5. **`docs/architecture.md` のツリー一致確認**: `git ls-files` から得た追跡対象ディレクトリの
   一覧が、`docs/architecture.md`「ディレクトリツリー」節の記載と一致するか確認する。
   既存プロジェクトで実ツリーから起こした場合は特に、書き漏らしがないか確認する
