# 設計済みタスクワークフローのモデルルーティング

この文書は、`execute-task`・`amend`・`follow-up`、およびそれらへ接続する計画工程(`elaborate`・`breakdown`)で使うモデル役割の正本である。モデル間の対応は総合性能の等価関係ではなく、十分に設計済みのタスクを扱う本ワークフロー上の役割対応とする。

| 役割 | Codex | Claude Code |
| --- | --- | --- |
| 通常の実装・検証 | Luna high | Sonnet high |
| 既存設計内の難しい実装・デバッグ | Terra high | Opus high |
| 既存設計内の特に複雑な実装・デバッグ | 必要に応じて Sol high | Opus high |
| 節目の横断的な `follow-up` | Terra high 以上 | Opus high 以上 |
| 設計の部分改訂(`amend`。設計書の目的・スコープは不変) | Terra high 以上 | Opus high |
| 設計・計画そのものの再検討(目的・スコープ・フェーズ構成の変更) | Fableを使う計画工程へ戻す | Fable |

**分業の目的**: 上位モデルの利用枠(Claude Code / Codex の利用上限)を設計と計画に充てるため、実装は通常実装の役割のモデルが担う。実行中に計画工程へ戻ると上位モデルの枠を消費するので、判定を要する規則は上流(設計書)で確定させ、タスクには規則に当てはめる作業だけを残す。これは設計書とタスクを書く側への要請であり、実装する側の停止条件(下の「次の場合だけ…停止し」)を弱めるものではない — 止まるべき時に止まらず、固定された契約を実装側で変えるほうが、後の手戻りで上位モデルの枠を多く使う。

**分解の基準となる実行者** は、通常実装の役割のモデルである。`elaborate`・`breakdown`・`amend` は、このモデルが上位モデルの判断なしに走り切れる設計書とタスクを書く。そのための記述の要件はこの文書に置かない(正は `skeletons/design.md` の「実行者の裁量と停止条件」「段階と分解の指針」「落とし穴」と、`commands/breakdown.md` の共通の前提・分割の規則)。個々の T に予定モデルを付けることとは別の話であり、下の「モデル名を個々のTの仕様や完了条件へ固定しない」は変わらない。

通常の `execute-task` は、`plan.md`、設計書、`TODO.md` に対象・依存関係・完了条件・検証内容が十分に着地していることを前提とする。コード調査、既存設計内の局所判断、実装、試験、完了条件の照合は通常実装モデルの責務であり、新たな大規模設計は含めない。

実行環境が現在のモデルを示す場合、対象役割の基準より下なら作業を始めず、必要なプロファイルでの再実行を提案する。基準以上のモデルで既に動いている場合は、標準モデルへ下げるために中断しない。Claude CodeコマンドとCodex skillはホストのモデルやeffortを固定しない。固定すると上位プロファイルでの再実行も標準値へ戻してしまうためである。グローバル設定を通常実装の標準値とし、各ワークフローは現在のプロファイルが役割を満たさなければ、選択済みと偽らず停止・再実行を案内する。

次の場合だけ、対象Tを未完了のまま停止し、理由と観測事実を示してルーティングを提案する。モデル変更の要否を平常時に利用者へ問い続けない。

- 原因不明のテスト失敗や不具合を通常の調査で絞り込めない
- 実装の複雑性が想定を超え、現在のモデルでは十分な確信を持って変更できない
- 完了条件を満たしたと十分に確認できない
- 対象Tの範囲を大きく超える変更が必要になった
- 現在のコードと設計書またはTODOに実質的な不一致がある
- 非自明な設計判断、`plan.md`、または設計書そのものの変更が必要になった

既存設計内に収まる難しい実装・デバッグは、Codexでは Luna high → Terra high → 必要に応じて Sol high、Claude Codeでは Sonnet high → Opus high の順に提案する。設計判断や計画変更が必要なら、実装モデルを上げ続けず `execute-task` を止め、変更の大きさで差し戻し先を分ける。設計書の「方針・構成」節または完了条件の改訂で足り、「目的」「スコープ / 非スコープ」と `plan.md` のフェーズ構成が変わらないなら `amend`(部分改訂の役割のモデル)へ、それらが変わるなら Fable を使う計画工程(`elaborate` → `breakdown`)へ差し戻す。分類の正は `BLUEPRINT.md` §6「変更の三段分類」。穴一つのために Fable で設計書全体を読み直さないことが、この区別の目的である。

部分改訂を Opus high / Terra high 以上とするのは、設計書を書き換える判断を最下位の実装モデルに任せず、かつ Fable の起動を再計画の時だけに絞るためである。この対応は実測前の仮定であり、`amend` の改訂案の質が足りないと観測されたら、この表の該当行を変更する。

モデル名を個々のTの仕様や完了条件へ固定しない。`TODO.md` にモデルの事前選択を持たせず、`実` 列には実際に完了させた実行系とモデルだけを記録する。標準モデルとエスカレーション先は今後の実測に応じてこの文書で変更し、各コマンドとskillはこの正本を参照する。通常実装のグローバル既定を変える場合は、Claude Codeでは `.claude/settings.json`、Codexでは `.codex/user-config.toml` をこの表と同じ変更で更新する。
